# 0008 — Tabulated stopping power: interpolation, range integral, V0 acceptance

- Status: accepted
- Date: 2026-09-10
- Task: DEV-003
- Affects: physical accuracy, numerical accuracy, validation strategy, performance, scientific interpretation

## Problem

`REQUIREMENTS.md` requires an external/tabulated physics layer alongside the
analytical one (decision `0006`), exposed through the *same* interface so
transport does not care which supplies a quantity. The first tabulated
quantity is the proton stopping power in water. This decision fixes, before
the comparisons are run: the interpolation scheme, the CSDA-range integral
and its low-energy treatment, and the acceptance criteria closing milestone
**V0**.

## Context and evidence

Research (Claude physics-researcher subagent, 2026-09-10; sources: NIST STAR
methods `https://physics.nist.gov/PhysRefData/Star/Text/programs.html`,
MCsquare source at commit `211eefe6`, Geant4 `G4PhysicsVector`):

- The MCsquare file `Materials/Water/PSTAR_Stop_Pow.dat` (801 rows, 0-400 MeV
  in 0.5 MeV steps) holds **total** (electronic + nuclear) mass stopping
  power. Its rows at the 51 native PSTAR grid energies are the
  4-significant-figure PSTAR values; the other 749 rows were generated by the
  MCsquare authors. Nuclear stopping is ≤ 0.1 % of the total above 0.5 MeV
  (0.098 % at 0.5 MeV, 0.04 % at 10 MeV, 0.026 % at 400 MeV), so the file
  equals the electronic stopping power to its four significant figures at
  therapeutic energies and is compared directly with the electronic analytic
  model. The 0 MeV row (129.7253) is a non-physical extrapolation artifact
  and is dropped.
- Reconstructing the 749 generated rows from the 51 native nodes shows they
  are a **monotone cubic Hermite (PCHIP) interpolation in E**: below ~300 MeV
  every generated row is reproduced to < 1e-8 relative, with small deviations
  only above 300 MeV (different end-derivative). Linear-in-E (what MCsquare
  itself uses at transport time) has up to 2.4 % error at 1-2 MeV; log-log
  linear ~1.6e-3; PCHIP ~1e-8 against the file and ~1e-5 against the
  underlying model above 1 MeV — far below PSTAR's own 1-4 % data uncertainty.
- NIST PSTAR CSDA ranges for liquid water (material 276), retrieved
  2026-09-10 from `https://physics.nist.gov/cgi-bin/Star/ap_table-t.pl`
  (g/cm²): R(0.5)=8.869e-4, R(1)=2.458e-3, R(10)=0.1230, R(100)=7.718,
  R(150)=15.77, R(200)=25.96, R(250)=37.94, R(400)=82.25. The residual CSDA
  range below the 0.5 MeV table floor is 8.869e-4 g/cm² (8.9 µm of water),
  below 1 MeV 24.6 µm — three orders of magnitude below a dose voxel.
  MCsquare's linear extrapolation through the 0 MeV row overestimates the
  sub-0.5 MeV range by 2.3×; it is discarded.

## Candidate approaches (interpolation)

1. **Linear in E** (MCsquare transport). Rejected: 2.4 % S error at 1-2 MeV
   is a visible Bragg-peak/LET artifact for a negligible saving.
2. **Log-log linear.** Good (1.6e-3), one `exp` per evaluation, was the first
   implementation here; rejected in favour of PCHIP because it is 3-4 orders
   of magnitude less faithful to the data generator and biases S low.
3. **Monotone cubic Hermite / PCHIP in E (selected).** Reproduces the
   MCsquare data generator, is shape-preserving (no overshoot, unlike natural
   or not-a-knot splines, which oscillate at the low-energy end), needs no
   transcendentals, and its error against the underlying model is ≲ 1e-5
   above 1 MeV.

## Selected approach

Implemented as shared source in `ionmc.physics.tabulated`, prepared by
`ionmc.data.stopping_tables.prepare_stopping_table`, exposed by
`ionmc.tabulated_stopping_power.TabulatedStoppingPower` with the same method
names and units as `AnalyticStoppingPower`.

1. **Interpolation.** PCHIP slopes (Fritsch-Carlson with Moler's end rule, the
   MATLAB/SciPy `pchip` algorithm) are computed at every grid point at load
   time; evaluation is the cubic Hermite of the bracketing segment. The
   interpolant reproduces the grid values exactly.
2. **Segment location.** A fixed-count bisection (`ceil(log2 n)` iterations,
   `m.where` updates) so the shared source runs identically as a Warp
   function per thread, as float64 Python and vectorised with numpy
   (decision `0005`). A uniform-grid `floor(E/dE)` index would be faster but
   would hard-code the 0.5 MeV spacing; the bisection keeps the layer
   grid-agnostic. Revisit if profiling at Stage 1+ shows it matters.
3. **CSDA range.** The cumulative range at each grid point is precomputed by
   8-point Gauss-Legendre quadrature of 1/S over the Hermite interpolant of
   each full segment; a query integrates the partial last segment with a
   4-point rule and adds the cumulative value at the lower node. The range
   below the first grid energy is **not** included; callers add the tabulated
   residual (8.869e-4 g/cm² at the 0.5 MeV floor) when comparing with a range
   defined from rest. The two quadrature rules agree to ~1e-7 over a full
   segment.
4. **Out-of-range energies** raise by default; `allow_extrapolation=True`
   continues the boundary segment's cubic.
5. **Second data source.** `mcsquare-g4-water` (Geant4-derived) is registered
   and loadable through the same class, giving a model-variation study for the
   configurable-physics-source requirement.

## Acceptance criteria (fixed before the comparison), milestone V0

| comparison | criterion |
|---|---|
| tabulated (PCHIP) reproduces the committed 20-point PSTAR subset | bitwise (rtol 1e-12) |
| tabulated vs analytic (decision 0006), 10-400 MeV | ≤ 1.0 % |
| tabulated CSDA range + 0.5 MeV residual vs NIST PSTAR at 100/150/200/250 MeV | ≤ 0.1 % |
| analytic CSDA range + 1 MeV residual vs NIST PSTAR at 100/150/200/250 MeV | ≤ 0.5 % |
| PCHIP exact for cubic data; slopes monotone; grid values reproduced | exact / shape checks |
| numpy binding vs Python binding | bitwise equal |
| float64 reference vs float32 Warp (CPU, CUDA) | S rtol 1e-5; range rtol 2e-5 (decision 0005) |
| Warp CPU vs CUDA | transcendental class: rtol 4e-6, atol 1e-6 (decision 0001) |

## Rationale

PCHIP is the scheme the reference data were built with, so the table layer
reproduces its source rather than adding a second interpolation model on top.
Keeping the range's low-energy floor explicit and documented (rather than
extrapolating through a non-physical 0 MeV row) is both more accurate and
honest about what is neglected. Sharing the interface with the analytic layer
means Stage 1 transport selects a data source without code changes.

## Expected tradeoffs

- PCHIP stores a slope per grid point (one extra float32 array per table);
  negligible for a handful of materials, revisit for hundreds.
- The bisection is O(log n) per evaluation versus O(1) for a uniform-grid
  index; chosen for grid-independence, flagged for the Stage 6 performance
  pass.
- The table is total stopping power; using it as electronic is accurate only
  because nuclear stopping is ≤ 0.1 %. When restricted stopping power is
  needed (delta-ray production in transport, Stage 1/2), this must be
  revisited so delta-ray energy is not double-counted.
- The tabulated CSDA range integrates the total stopping power, consistent
  with PSTAR's own range definition.

## Validation strategy

`tests/ionmc/test_tabulated.py` (reference paths, every criterion above except
Warp; PCHIP exactness and the reconstruction of MCsquare's rows from the
native nodes), `tests/ionmc/test_data_layer.py` (parser, slopes, quadrature),
and `validation/v0_tabulated_stopping_power.py` on the host runner for the
Warp paths and the full gate set at the exact SHA.

## Validation outcome

*Reference paths (sandbox, Python 3.12, numpy 2.x; Warp CPU float32 also):*
tabulated reproduces the committed PSTAR subset bitwise; tabulated vs analytic
over 10-400 MeV is within +0.25 % (worst at 11 MeV, an MCsquare-interpolated
row); tabulated CSDA range + residual vs NIST PSTAR is within 1.8e-4
(100 MeV -7.7e-5, 150 MeV +7.0e-5, 200 MeV -1.8e-4, 250 MeV -1.3e-4);
analytic range + residual within 5.3e-4; numpy and Python bindings bitwise
equal; PCHIP exact for cubic data and slope-monotone. The Geant4 table is
0.4-0.5 % below the PSTAR table, matching the ICRU 90 vs ICRU 49 analytic
offset. Warp CPU float32 vs the float64 reference passed the decision 0005
criterion in the sandbox.
